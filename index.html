01In daily use, spending real money

Domain auction sniper

Built for a domain investor at eWorldWideWeb · May 2026 to now · code on GitHub

935klistings indexed daily 1.5sbid before close 21klines of code 287tests

It has bought domains fully hands off while the client slept, including names like neosono.com and shackmax.com that it held through a dead auction and grabbed the instant they relisted at $50. He's a 28 year veteran of GoDaddy's expiring list with 20,000 domains, not technical, and he now runs his sourcing through this tool instead of the 45 minutes a morning he used to spend scrolling by hand.

Each day it indexes about 935,000 live listings, scores them against what he actually buys, and shows him 30,000 ranked names with GoDaddy and Estibot valuations side by side. He sets a max bid and walks away: the bid fires 1.5 seconds before close. The bidding strategy is his, encoded as one pure function we rewrote together after he watched the first version fire live and changed his mind. Its one hard rule: never place the first bid on a no bid auction, because that attracts competition. Let it die, then buy the closeout. If he gets outbid he gets one text. If he's already bidding on a name himself, the tool stands down rather than bid against him.

It spends real money with no sandbox

GoDaddy's test environment doesn't work for these APIs, so every call is production. Every purchase passes a per purchase cap, a daily cap, a sanity check against the reference price, a kill switch, double buy locks, and a single checked path for dollar conversion, where a slipped decimal turns $2,600 into $26,000. Over the cap, the dashboard asks him to confirm the exact amount instead of silently refusing.

What I got wrong

The guards never failed. Observability did.

A real money system can look perfectly healthy while doing nothing. Twice this cost an auction. Once the worker hung for 19 hours with no errors, so I built a heartbeat, a watchdog, and a hard deadline on every cycle.

The harder one: GoDaddy had been rate limiting us for weeks, the ban text came back unparseable, the parser called it "false," and the worker read false as "nothing for sale" and waited while the client bought the domain by hand in front of it. I rebuilt the state model so "unknown" can never be mistaken for a fact, added a circuit breaker that goes silent long enough for the ban to expire, wired a second price source so one blind sensor can't blind the system, and made the dashboard turn red. Then I wrote a script that rebuilds any domain's full timeline from the database, because by the time you ask "why didn't it buy," the logs are gone.

02Live, first Stripe sale Sept 2026

Nameway.com

eWorldWideWeb · 2026 · nameway.com

20,000+domains for sale 19,460vector logos 38 MBfor all of them hourlyregistrar sync

Nameway is the storefront for a portfolio of more than 20,000 domains. The old site was hard to shop, its inventory drifted out of sync with the registrar, and there was no way to pay online. I rebuilt it in WordPress, then kept building, because a store this size only works if it runs itself. The first Stripe sale came in September 2026.

What's running today

  • A custom theme with a search grid, A to Z and by-length browsing, industry pages, and a landing page for every domain, so each name can rank in search on its own.
  • A checkout plugin: Stripe (card and ACH) under $5,000, an Escrow.com flow above it. Webhook signature verification, the async events ACH settlement needs, confirmation emails from a real mailbox instead of "WordPress", and listings that take themselves down when they sell.
  • An hourly sync against the GoDaddy account: sold names come off the site, new ones stage as drafts, and a dry-run report prints first so nothing changes by surprise.
  • Industry classification built on the 45 USPTO trademark classes, installed as a real taxonomy with buyer-friendly names and applied in reviewed batches with a human check, never one unchecked pass.

The logo pipeline: 19,460 vector logos

Every listing needed artwork, so I built a pipeline around an AI design agent I direct. It generates true vector SVG wordmarks: 19,460 of them at about 38 MB total, where raster images would have run past a gigabyte. Letters are outline paths drawn from the domain string, so a misspelled logo is mechanically impossible. A server-side toolchain imports each file, attaches it as the listing's featured image, crops the viewBox, and caches per-logo geometry so letters render at equal height across 19,000 cards regardless of font or icon.

The part I would defend hardest in an interview is the verification discipline. The generator grades its own work, and I never let that be the only grade. My independent audits caught 4,803 bad word splits on the first pass and 255 more on the second, and the fix that stuck replaced a dictionary with frequency scoring against the catalog's own vocabulary: "heat" appears 38 times in the corpus and "theat" once, so sportheat splits after sport. Names that failed review shipped on a holdback list instead of blocking the other 98 percent. And when the client later changed the entire visual direction, the same wave pipeline repainted all 19,000 logos in an afternoon.

What broke, and what it taught me

  • Logos imported by a root process came out root-owned. Apache refused to serve them, a redirect plugin bounced every image URL to the homepage, and the symptom read as broken images when the disease was file permissions. Ownership repair is now a step inside the pipeline, not a cleanup after it.
  • The site dropped into maintenance mode at 14:30 two days in a row. The same minute twice is a schedule, not a coincidence: a cron-driven auto update kept dying mid-flight and leaving its lock file behind. I disabled auto updates and made updating a deliberate, backup-first task.
  • My CLI tooling fataled twice for different reasons: a plugin's filesystem check pushes WordPress into FTP mode when run as root, and a core function my script relied on had been removed in a newer WordPress. Same lesson both times: plain prepared queries and an explicit filesystem method beat convenient wrappers that change underneath you.
  • WordPress files each upload under its parent post's date, so 500 logos scattered across month folders going back to 2020 and my first maintenance script only swept the current month. My globs now match what the system actually does, not what I assumed it does.

Hardening, and where it's going

I also cleaned up the server itself: deleted a web-readable backup file that had been exposing payment gateway credentials, had the key rotated, forced every SVG upload through a sanitizer, and retired stale themes and dependencies.

The next step is convergence. Import, classify, generate, and attach already exist as separate proven tools, and they are becoming one intake command: a new price sheet turns into listings, categories, and logos with a review report, instead of a day of manual work. The human stays where judgment matters, approving low-confidence classifications and new artwork, and the machine does the rest.

04Running the label

Label manager agents and the Deep Steppe Desk

Deep Steppe · 2026 · Claude agents, skills and scheduled tasks

3Claude agents 40+curator pitches for one single 0sends without my approval

Deep Steppe is my house label. Every release so far has sold out, but each one comes with a long list of chores: distributor uploads, playlist and radio pitching, socials, press emails and shipping, on top of signing artists and manufacturing. Running it alone, things slipped.

I set up a small team of Claude agents to take on that work. A label manager agent keeps the release calendar and hands tasks to two others: one builds releases with our distributor, the other handles pitching, submission forms, socials and press outreach. None of them can pay for, send or submit anything that needs my approval without it. Everything they do shows up on one dashboard, the Desk, where each release, task and outreach contact links straight to the page or form it needs and gets checked off as it's done.

What the Desk covers

  • Releases: every release on the calendar with its date, its distributor status and links to the store and streaming pages, so I can see what's left before it ships.
  • Needs Adam: the short list of things only I can do, like a login, a purchase or a signature, each one linking to the exact page.
  • The outreach pipeline: every playlist curator, radio station and press contact, where they stand from drafted to sent to replied, and a link to the outlet or form. For one single, the agents sent individual pitches to more than 40 curators and filled out the free submission forms on their own.
  • Drafts waiting on me: pitch emails sit on the Desk with Read draft and Approve buttons. Nothing goes out until I approve it, and once I do, it goes to the whole list.
  • Deadlines and socials: pitch windows, submission deadlines and the posting schedule, plus scheduled check-ins, like pulling streaming numbers a few days after a release and pitching another round if they're low.
  • Shipping: for our CD release, the agents made a shipping label for every order, cropped them for the label printer, and marked each Bandcamp order shipped with its tracking number in the buyer email.
  • Message the team: a chat panel on the Desk where I give the agents instructions from my phone, and they pick them up in their next session.

How it gets better on its own

The Desk updates itself. When an agent finishes something, it checks it off without me asking. And whenever I have to step in, the agent writes what it learned into a shared skill file, so the next run handles that case without me. That's how a curator email that once sat unsent through a release week became a rule: drafts go up for approval the same day they're written.

05Live, open source

Auto DM

For Deep Steppe and YOON Fest · 2026 · code on GitHub

$0a month to run ~1,900lines per postticket attribution

The label and the festival sell records and tickets on Instagram. Comment to DM tools like ManyChat work, but they cost money every month and can't tell you which post actually sold the tickets. So I wrote my own.

Someone comments on a post and gets a DM with the link. Each post can be set up for a release, for tickets, for a guestlist (it asks for their name by DM, caps the list and keeps a waitlist, and prints a door list), or for a sold out show, where it collects emails for the next batch. Every link in a DM is a tracked short link, and a sync with Shotgun, our ticketing platform, counts each ticket bought through a DM against the post that sent it.

Instagram webhooks deliver comments instantly once Meta approves the app; until then, and as a backup, it checks for new comments every minute. The same Worker also serves the deepsteppe.com homepage and its mailing list signup.

Moving a client site off an agency's hosting

eWorldWideWeb · September 2026

A client's company site had been rebuilt and hosted by an outside agency, and the agency's hosting was ending at the end of the month. I had a 487 MB site backup, a login, and a deadline. On the client's own server I backed up and retired the old 2012 account for the domain, set up a fresh account on PHP 8.2, installed WordPress from the command line, and imported the site by extracting the backup by hand. I updated the company's address and phone numbers across the site with a database backup taken first.

The tricky part wasn't the server. The domain turned out to live in a different registrar account than the one we had access to, so I exported the current DNS records and worked with the registrar's account manager on the cutover. SSL was issued as soon as it pointed at the new server, and every backup was kept. Checking the records also showed the inquiry address on the site had no mail records set up, so I flagged it to the client to decide where those emails should go.

In progress, becoming an app

Discogs bulk lister: photos in, a seller inventory out

Personal · 2026 · for selling my own records

I'm selling a large batch of dance 12"s on Discogs. Listing them one by one is slow, and the hard part isn't reading the label. It's picking the right pressing when several releases share one catalog number. I built a method with Claude that turns phone photos of center labels into a Discogs bulk upload file.

  • It matches on the strongest signal first: catalog number, then barcode, runout etching, track lengths, credits, label design and vinyl color. Artist and title alone are close to useless.
  • It doesn't guess. When two releases differ only by something the photo can't show, like vinyl color or a runout, it names the exact check and which release each answer leads to.
  • Pricing is auditable: the median asking price, or last sold plus $10 when nothing is listed. It always shows the sold median next to the asking median and flags records where sellers are asking far more than buyers have actually paid.
  • Output is the upload CSV in my seller account's exact column order, a pricing file showing how every price was set, and a checklist of what to verify before uploading.

Next I'm turning it into an app other sellers can use.
